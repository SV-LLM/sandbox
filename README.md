# SV-LLM Sandbox

Provider-neutral collaboration plane for SV-LLM. Sandbox admits bounded work bound to a receipted SV-LLM parent transition, assigns capabilities to registered entities, requests and records their contributions, and records a synthesis that preserves every contribution's lineage, disagreement, refusal, unavailability, failure and uncertainty.

Every attempted transition yields one receipt in this repository's transition ledger, whether it is allowed or denied, and each receipt propagates to the SV-LLM organization ledger. In the authentic live lane that ledger is kept in its declared subtree of the SV-LLM organization ledger ref (`repository_ledger_location` in `.stegverse/transition-ledger/contract.json`), so each run continues the chain the last one published. Sandbox-to-entity dispatch is intra-organization. Participation creates no governance authority.

Contracts: `sv-llm.sandbox-work/v0.1`, `sv-llm.contribution/v0.1`, `sv-llm.entity-capability/v0.1` and `sv-llm.capability-id/v0.1` in SV-LLM/schemas, serialized and digested under `SV_LLM_CANONICAL_JSON_V1`. Entity registration is evaluated by SV-LLM/.github `org-runtime/sandbox_registration.py` against the canonical organization tree.

## StegBrowser llm.v1 tool

`runtime/stegbrowser_tool.py` lets admitted Sandbox work call an LLM web page through StegBrowser's `llm.v1` profile, vendored byte-for-byte from StegVerse-Labs/StegBrowser `3900aa2` in `runtime/vendor/stegbrowser_llm/` (digest manifest included). StegBrowser's own llm.v1 tests are standard-library `unittest` tests and run against those bytes through `tests/run_stegbrowser_upstream.py`, so CI installs nothing. llm.v1 never waits on the provider: `wait_for` is refused, an action whose target is not on the delivered page fails at once, and `read_text` reads what the page holds at that moment, so an answer not yet rendered is a recorded non-success that a later manifest may retry. Each call opens a fresh Chromium context over ordinary HTTPS and destroys it afterward; the Sandbox ledgers are not ephemeral. The path has no LLM-adapter hop and no InTr hop; that rule applies to internal admitted Sandbox operations only, which need not traverse the adapter again. External provider/LLM ingress follows the declared path: healthy node -> LLM-adapter -> SDK -> StegVerse-org/.github -> Interlock/InTr => Org Ledger.

The call is declared in the work object at `manifested_request.tool_invocations[]`. Before StegBrowser runs, Sandbox checks that the work is admitted, the invocation is declared, the prompt and target origin match the admitted values, and it issues the lease itself (`task_id` = `work_id`). Every attempt, including a Sandbox-side DENY, is recorded as `SANDBOX_TOOL_OBSERVATION_RECORDED`. A browser result is a tool observation, not an entity contribution; provider and model names are labels, not attestation. Synthesis binds every contribution and every tool observation. A failed organization propagation is recorded as `ORGANIZATION_PROPAGATION_FAILED` and blocks completion until `repropagate()` succeeds.

The live lane (`live/run_live_llm.py`) has no workflow: GitHub-hosted runners are external machines, so the earlier manual runner workflow was retired. The lane runs only where a manifest admits it on a canonical runtime substrate; until then it holds SV-LLM/.github SV-LLM-EXEMPTION-002, because it still takes its organization-execution identity from `GITHUB_REPOSITORY`. Earlier runner results remain CI-class evidence only, never SANDBOX_RUNTIME_OBSERVED. Stage 1 targets a StegVerse-controlled conformance page, `https://stegverse.org/integration/llm-browser-test/v1/` (served from StegVerse-Labs/Site), configured in `live/target.json`. It proves only the live browser path: no provider attribution, and no provider or model labels are sent. The lane fails closed until that target is verified. Each `SV-LLM/<Provider>` repository records its provider's published access policies under `access-policy/` (`sv-llm.provider-access-policy/v0.1`) as stated awareness; those records have no gating effect.

## Work cycle

`runtime/work_cycle.py` is the Sandbox side of the SV-LLM work cycle. SV-LLM/.github `org-runtime/crossing.py::ingress` materializes a manifest addressed to `sandbox` in the supplied node state and records `ORGANIZATION_INGRESS_MATERIALIZED`. One pass of the work cycle then:

1. takes each materialization in once. Processing is selected only by the manifest's `processing.capability` bound to `processing.route_id`, which this service must admit (`runtime/contracts/sandbox-service.json`, evaluated by SV-LLM/.github `manifest_selection.py`).
2. admits the work, using the ingress receipt pair read back from the organization ledger as its parent, then assigns each declared participant and requests its contribution. When the work names `participants: "DERIVE_FROM_DECLARATIONS"`, `runtime/capability_routing.py` derives them: each requested capability goes to the first registered entity, in the canonical organization tree's row order, whose own `contracts/entity-capability.json` declares it (an entity surface not on the tree is never routed to), the other declaring entities are recorded as alternates, and a capability no registered entity declares is refused with the six actionable fields (`PARTICIPANTS_DERIVABLE_FROM_DECLARATIONS`). Nothing about an entity's availability is consulted; routing selects who is asked and confers no authority. The selection output of SV-LLM/Ecosystem_Chat `classify.py` (`sv-llm.capability-selection/v0.1`) is a valid `requested_capabilities` source. `tests/test_work_cycle.py` runs that path end to end: a question text through the vendored Ecosystem_Chat classifier (`tests/real_entities/Ecosystem_Chat`, pinned in `vendor-manifest.json`) to a derived assignment, an answer and an egressed result.
3. lets each entity answer through its own package. No SV-LLM code invokes a model: until an admitted Sandbox tool does, with credential bytes stored exclusively in the SKAP Vault inside KV, scoped by TV/TVC authority and accessed only by admitted manifest transitions (an InTr transition only where the access crosses between two distinct organizations; never an InTr hop inside one organization, Rigel's rule 2026-10-25), an entity answers `UNAVAILABLE NO_ADMITTED_INVOCATION_SURFACE`. A request whose entity surface the pass does not supply terminates in the same pass at E0: the Sandbox records `UNAVAILABLE ENTITY_SURFACE_NOT_SUPPLIED` bound to the pass's entity-set digest, with a six-field `FAIL_CLOSED` (`e0_terminal`), and the work closes. Nothing stays outstanding, waits or polls.
4. synthesizes and completes work whose every request is answered, and egresses the result to the organization the manifest's `return_to` names. The mesh is the durable queue; nothing waits for the receiver.

Every attempt is a receipt propagated to the organization ledger, and a second pass changes nothing. `tests/test_work_cycle.py` runs the cycle end to end offline: a peer organization's manifest goes in, a result goes back, and the peer consumes it. One case assigns all 18 intelligence providers in the canonical organization tree; each registers against its digest-bound declaration and answers through its own core package (vendored in `tests/real_entities`, bound by `vendor-manifest.json`). That is CI-class evidence; running the same pass on a StegVerse substrate is what would make it runtime-observed.

## Provider capability contract

`runtime/contracts/provider-capability.schema.json` (`sv-llm.provider-capability/v0.1`) fixes the structure of each `SV-LLM/<Provider>` repository's `capability.json`. `runtime/provider_capability.py` is the offline validator those repositories vendor byte-for-byte (each records its sha256 in `validator_ref`). It returns ALLOW, DENY or FAIL_CLOSED: FAIL_CLOSED for malformed declarations or unbound provenance (an operation marked DOCUMENTED or UNSUPPORTED must cite a fetched page); DENY for authority claims, credential or endpoint material, live-invocation or runtime-observation claims, an authentic interface without a receipt, or a foreign identity. Negative fixtures are in `tests/fixtures/provider_capability/negative/`. The validator contacts no provider, and its disposition is evidence about a source file, not a transition.

## Conformance proposal check

`runtime/conformance_proposal.py` is the Ecosystem Chat sandbox check described in SV-LLM/StegVerse_AI `docs/CANONICAL_INVARIANT_AVAILABILITY_AND_ECOSYSTEM_CHAT_SANDBOX_ENFORCEMENT.md`. Before an approved solution is proposed to the SDK, it evaluates the `stegverse.ai-invariant-conformance-proposal/v1` artifact against the canonical sources the caller resolved and passed in as bytes; it fetches nothing.

- It computes the applicable set itself: every `invariants` key and `prohibitions` entry of each cited `stegverse.task-registry-global-invariants/v1` document. Prompt wording and the proposal's author have no effect.
- It recomputes each source's digest.
- It inspects the proposed changes themselves for added dependency manifests, installs, schedules, sleeps or polling, and any canonical `false` invariant set to true.

The disposition is:

- FAIL_CLOSED when the proposal cannot be evaluated: a source is missing, unbound or conflicting, coverage is incomplete, an assessment lacks evidence, or an invariant is left unresolved.
- DENY when it is nonconforming: an invariant violation, an added dependency, routing by model/provider/repository identity, self-declared conformance, an inflated evidence class, a claimed runtime transition, or a settled finding reopened without new evidence.
- ALLOW otherwise.

Each non-ALLOW outcome carries the six conformance fields. ALLOW only lets the proposal be offered to the SDK; it is not an SDK, Interlock/InTr or Organization disposition. `tests/test_conformance_proposal.py` covers the document's acceptance tests against a synthetic canonical fixture.

## Stage 2 page load (first test)

`runtime/page_load_tool.py` adds the StegBrowser `page_load.v1` profile: admitted work declares a provider's public URL and lease origins; Sandbox checks the invocation (admitted, declared, well-formed, no prompt/selector/credential field, URL inside the lease), then opens the vendored `EphemeralBrowserSession` lease (`navigate` and `read_public` only, no persistent profile, cookies, history or credentials), loads the page in a fresh Chromium context with main-frame navigations outside the lease aborted, takes a screenshot and closes the session. The observation is the page as delivered (`DOMContentLoaded`): nothing waits for the provider to go idle or settle, because waiting on an external machine is not a transition predicate. Every attempt is a `SANDBOX_TOOL_OBSERVATION_RECORDED` receipt carrying the HTTP status, final URL, title, screenshot digest, refused navigations and the lease's terminal receipt. An HTTP 403 or bot challenge is recorded as observed, not bypassed. Nothing is typed, clicked or submitted, so this is not provider interaction and no provider contract is consulted.

No GitHub workflow executes this profile. Under the ecosystem invariants (`StegVerse-Labs/.github` `data/task-registry-global-invariants.json`) GitHub/CI has no runtime authority and no external machine may be a dependency: page load is a manifest-bound attempted transition, the Sandbox admits the work and records the observation, and the StegBrowser lease executes on a substrate from the canonical runtime substrate order; an unavailable receiver is answered by `DURABLE_QUEUE_OR_EVENT_EPHEMERAL_MATERIALIZATION`, never by waiting. The earlier GitHub-hosted runner path (`sandbox-stage2-page-load.yml`, run 38182253802 and 38183492932) was removed as non-conforming; its outputs are CI-class evidence only.

## Invariant question evaluation (RT-INVARIANT-EVALUATION-001)

`runtime/invariant_evaluation.py` answers one structured question about one canonical invariant: `stegverse.invariant-question/v1` names an `invariant_id` (`invariant:<key>` or `prohibition:<NAME>` from StegVerse-Labs/.github `data/task-registry-global-invariants.json`), one subject document and the exact revisions of both; the caller passes the bytes, and the component fetches nothing and calls no GitHub API. The answer (`stegverse.invariant-evaluation/v1`) is ALLOW when every assertion the subject makes about the invariant equals the canonical value, DENY when any assertion contradicts it, FAIL_CLOSED when the question or a source cannot be bound (every cited source carries a digest that is verified before its bytes are parsed; the question bytes go through the same bounded parser as every source, and the spec's declared bounds are mirrored one for one (question bytes 65536, each source 4194304 after its digest matches, 16 sources, 100000 items per container, 512 code points per string field; the CLI reads at most 65537 question bytes), so nesting past 64 open containers is `INPUT_DEPTH_EXCEEDED`, an exceeded size or count is `INPUT_SIZE_EXCEEDED`, an over-long field is `INPUT_FIELD_INVALID`, duplicate keys are `JSON_DUPLICATE_KEY` and running out of bytes is `JSON_TRUNCATED`, each cited at the line parsing stopped on; a canonical source without an allowed `authority_effect` is `SOURCE_AUTHORITY_EFFECT_NOT_ALLOWED`, cited at that member), and UNDECIDABLE when the subject is silent or the invariant is not declared in the supplied canonical bytes (cited at the declaring container): silence is never read as conformance, and an UNDECIDABLE answer writes one write-once relay-queue entry keyed by `evaluation_key` = sha256 of `question_sha256` (the exact question bytes) plus the sorted source bindings (the same bytes over the same sources is one entry; different bytes or sources are another; nothing is overwritten) for a reader with more evidence. The answer's `owning_existing_goal` is the question's once the question is well-formed (its form is checked as a canonical task id); a refusal before that carries the fixed owner `STEGVERSE-CANONICAL-WORK-COORDINATION-001`, which owns the evaluator. `evaluate_bytes` is the entrypoint for raw question bytes and is what the CLI uses. Every answer cites `repo@revision:path:line`; every non-ALLOW answer carries the six actionable fields. `authority_effect` is NONE_ANSWER_ONLY: it answers, it does not transition. `tests/test_invariant_evaluation.py` runs offline against byte-for-byte copies of canonical Labs files pinned in `tests/fixtures/invariant_evaluation/vendor-manifest.json`.

`runtime/conformance_proposal.py` asks this evaluator the same question per applicable invariant for every proposed JSON change, so a change that contradicts a canonical value is refused there with the evaluator's `path:line` citation; the evaluator's ALLOW and UNDECIDABLE answers leave the proposal's own assessment in charge of coverage. One evaluator, no drift.

Open bindings, recorded for the owner of `SDK-GENERIC-MANIFEST-ECOSYSTEM-INVARIANT-005`: the relay-queue entry schema is provisional until a queue locus is named, and `UNDECIDABLE` is not yet in the Labs `validate_transition_disposition.NON_ALLOW` vocabulary (alias to DEFER or add the term).

## Existing StegNode capability binding (PR #44)

`runtime/stegnode_capability_binding.py` is a non-authorizing, side-effect-free predicate evaluator. It does not create node registration, authenticate caller-supplied node/posture objects, read SKAP Vault credentials, or independently authorize a transition. Public retrieval requires no node. Protected work fails closed without an authentic InTr posture verifier and admitted manifest. Its result is **not** native InTr ALLOW, SDK route publication, a WorkerCoordinator claim/fence, or sovereign Organization Ledger readback. The isolated regression is executed in CI by `tests/test_stegnode_capability_binding.py`. Integration into `runtime/work_cycle.py` requires the original authenticated producer and route/manifest binding, not an injected untrusted verifier. No new runtime, hosted dependency or connected device is required.
