# SV-LLM Sandbox

Provider-neutral collaboration plane for SV-LLM. Sandbox admits bounded work bound to a receipted SV-LLM parent transition, assigns capabilities to registered entities, requests and records their contributions, and records a synthesis that preserves every contribution's lineage, disagreement, refusal, unavailability, failure and uncertainty.

Every attempted transition yields one receipt in this repository's transition ledger, whether it is allowed or denied, and each receipt propagates to the SV-LLM organization ledger. In the authentic live lane that ledger is kept in its declared subtree of the SV-LLM organization ledger ref (`repository_ledger_location` in `.stegverse/transition-ledger/contract.json`), so each run continues the chain the last one published. Sandbox-to-entity dispatch is intra-organization. Participation creates no governance authority.

Contracts: `sv-llm.sandbox-work/v0.1`, `sv-llm.contribution/v0.1`, `sv-llm.entity-capability/v0.1` and `sv-llm.capability-id/v0.1` in SV-LLM/schemas, serialized and digested under `SV_LLM_CANONICAL_JSON_V1`. Entity registration is evaluated by SV-LLM/.github `org-runtime/sandbox_registration.py` against the canonical organization tree.

## StegBrowser llm.v1 tool

`runtime/stegbrowser_tool.py` lets admitted Sandbox work call an LLM web page through StegBrowser's `llm.v1` profile, vendored byte-for-byte from StegVerse-Labs/StegBrowser `7353176` in `runtime/vendor/stegbrowser_llm/` (digest manifest included). Each call opens a fresh Chromium context over ordinary HTTPS and destroys it afterward; the Sandbox ledgers are not ephemeral. The path has no LLM-adapter hop and no InTr hop; that rule applies to internal admitted Sandbox operations only, which need not traverse the adapter again. External provider/LLM ingress follows the declared path: healthy node -> LLM-adapter -> SDK -> StegVerse-org/.github -> Interlock/InTr => Org Ledger.

The call is declared in the work object at `manifested_request.tool_invocations[]`. Before StegBrowser runs, Sandbox checks that the work is admitted, the invocation is declared, the prompt and target origin match the admitted values, and it issues the lease itself (`task_id` = `work_id`). Every attempt, including a Sandbox-side DENY, is recorded as `SANDBOX_TOOL_OBSERVATION_RECORDED`. A browser result is a tool observation, not an entity contribution; provider and model names are labels, not attestation. Synthesis binds every contribution and every tool observation. A failed organization propagation is recorded as `ORGANIZATION_PROPAGATION_FAILED` and blocks completion until `repropagate()` succeeds.

The live call (`.github/workflows/sandbox-live-llm.yml`) is manual and is a proof of concept: it runs on a GitHub-hosted runner, so its results are CI-class evidence at most, never SANDBOX_RUNTIME_OBSERVED, and it is not the manifest-bound execution path. Stage 1 targets a StegVerse-controlled conformance page, `https://stegverse.org/integration/llm-browser-test/v1/` (served from StegVerse-Labs/Site), configured in `live/target.json`. It proves only the live browser path: no provider attribution, and no provider or model labels are sent. The workflow fails closed until that target is verified. Its evidence is uploaded as a 90-day artifact: live-run evidence retention, not permanent custody. Each `SV-LLM/<Provider>` repository records its provider's published access policies under `access-policy/` (`sv-llm.provider-access-policy/v0.1`) as stated awareness; those records have no gating effect.

## Work cycle

`runtime/work_cycle.py` is the Sandbox side of the SV-LLM work cycle. SV-LLM/.github `org-runtime/crossing.py::ingress` materializes a manifest addressed to `sandbox` in the supplied node state and records `ORGANIZATION_INGRESS_MATERIALIZED`. One pass of the work cycle then:

1. takes each materialization in once. Processing is selected only by the manifest's `processing.capability` bound to `processing.route_id`, which this service must admit (`runtime/contracts/sandbox-service.json`, evaluated by SV-LLM/.github `manifest_selection.py`).
2. admits the work, using the ingress receipt pair read back from the organization ledger as its parent, then assigns each declared participant and requests its contribution.
3. lets each entity answer through its own package. No SV-LLM code invokes a model: until an admitted Sandbox tool does, with credentials held by TV/TVC, an entity answers `UNAVAILABLE NO_ADMITTED_INVOCATION_SURFACE`. A request with no entity surface stays outstanding for a later pass.
4. synthesizes and completes work whose every request is answered, and egresses the result to the organization the manifest's `return_to` names. The mesh is the durable queue; nothing waits for the receiver.

Every attempt is a receipt propagated to the organization ledger, and a second pass changes nothing. `tests/test_work_cycle.py` runs the cycle end to end offline: a peer organization's manifest goes in, a result goes back, and the peer consumes it. That is CI-class evidence; running the same pass on a StegVerse substrate is what would make it runtime-observed.

## Provider capability contract

`runtime/contracts/provider-capability.schema.json` (`sv-llm.provider-capability/v0.1`) fixes the structure of each `SV-LLM/<Provider>` repository's `capability.json`. `runtime/provider_capability.py` is the offline validator those repositories vendor byte-for-byte (each records its sha256 in `validator_ref`). It returns ALLOW, DENY or FAIL_CLOSED: FAIL_CLOSED for malformed declarations or unbound provenance; DENY for authority claims, credential or endpoint material, live-invocation or runtime-observation claims, an authentic interface without a receipt, or a foreign identity. Negative fixtures are in `tests/fixtures/provider_capability/negative/`. The validator contacts no provider, and its disposition is evidence about a source file, not a transition.

## Stage 2 page load (first test)

`runtime/page_load_tool.py` adds the StegBrowser `page_load.v1` profile: admitted work declares a provider's public URL and lease origins; Sandbox checks the invocation (admitted, declared, well-formed, no prompt/selector/credential field, URL inside the lease), then opens the vendored `EphemeralBrowserSession` lease (`navigate` and `read_public` only, no persistent profile, cookies, history or credentials), loads the page in a fresh Chromium context with main-frame navigations outside the lease aborted, takes a screenshot and closes the session. Every attempt is a `SANDBOX_TOOL_OBSERVATION_RECORDED` receipt carrying the HTTP status, final URL, title, screenshot digest, refused navigations and the lease's terminal receipt. An HTTP 403 or bot challenge is recorded as observed, not bypassed. Nothing is typed, clicked or submitted, so this is not provider interaction and no provider contract is consulted.

No GitHub workflow executes this profile. Under the ecosystem invariants (`StegVerse-Labs/.github` `data/task-registry-global-invariants.json`) GitHub/CI has no runtime authority and no external machine may be a dependency: page load is a manifest-bound attempted transition, the Sandbox admits the work and records the observation, and the StegBrowser lease executes on a substrate from the canonical runtime substrate order; an unavailable receiver is answered by `DURABLE_QUEUE_OR_EVENT_EPHEMERAL_MATERIALIZATION`, never by waiting. The earlier GitHub-hosted runner path (`sandbox-stage2-page-load.yml`, run 38182253802 and 38183492932) was removed as non-conforming; its outputs are CI-class evidence only.
