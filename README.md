# SV-LLM Sandbox

Provider-neutral collaboration plane for SV-LLM. Sandbox admits bounded work bound to a receipted SV-LLM parent transition, assigns capabilities to registered entities, requests and records their contributions, and records a synthesis that preserves every contribution's lineage, disagreement, refusal, unavailability, failure and uncertainty.

Every attempted transition yields one receipt in this repository's transition ledger, whether it is allowed or denied, and each receipt propagates to the SV-LLM organization ledger. In the authentic live lane that ledger is kept in its declared subtree of the SV-LLM organization ledger ref (`repository_ledger_location` in `.stegverse/transition-ledger/contract.json`), so each run continues the chain the last one published. Sandbox-to-entity dispatch is intra-organization. Participation creates no governance authority.

Contracts: `sv-llm.sandbox-work/v0.1`, `sv-llm.contribution/v0.1`, `sv-llm.entity-capability/v0.1` and `sv-llm.capability-id/v0.1` in SV-LLM/schemas, serialized and digested under `SV_LLM_CANONICAL_JSON_V1`. Entity registration is evaluated by SV-LLM/.github `org-runtime/sandbox_registration.py` against the canonical organization tree.

## StegBrowser llm.v1 tool

`runtime/stegbrowser_tool.py` lets admitted Sandbox work call an LLM web page through StegBrowser's `llm.v1` profile, vendored byte-for-byte from StegVerse-Labs/StegBrowser `7353176` in `runtime/vendor/stegbrowser_llm/` (digest manifest included). Each call opens a fresh Chromium context over ordinary HTTPS and destroys it afterward; the Sandbox ledgers are not ephemeral. The path has no LLM-adapter hop and no InTr hop; that rule applies to internal admitted Sandbox operations only, which need not traverse the adapter again. External provider/LLM ingress follows the declared path: healthy node -> LLM-adapter -> SDK -> StegVerse-org/.github -> Interlock/InTr => Org Ledger.

The call is declared in the work object at `manifested_request.tool_invocations[]`. Before StegBrowser runs, Sandbox checks that the work is admitted, the invocation is declared, the prompt and target origin match the admitted values, and it issues the lease itself (`task_id` = `work_id`). Every attempt, including a Sandbox-side DENY, is recorded as `SANDBOX_TOOL_OBSERVATION_RECORDED`. A browser result is a tool observation, not an entity contribution; provider and model names are labels, not attestation. Synthesis binds every contribution and every tool observation. A failed organization propagation is recorded as `ORGANIZATION_PROPAGATION_FAILED` and blocks completion until `repropagate()` succeeds.

The live call (`.github/workflows/sandbox-live-llm.yml`) is manual. Stage 1 targets a StegVerse-controlled conformance page, `https://stegverse.org/integration/llm-browser-test/v1/` (served from StegVerse-Labs/Site), configured in `live/target.json`. It proves only the live browser path: no provider attribution, and no provider or model labels are sent. The workflow fails closed until that target is verified. Its evidence is uploaded as a 90-day artifact: live-run evidence retention, not permanent custody. Provider-specific live calls (Stage 2) resolve their surface from each `SV-LLM/<Provider>` repository's own interaction contract (`sv-llm.provider-interaction-contract/v0.1`), never from `live/target.json`. `runtime/provider_contract.py` resolves the contract of the entity assigned to the work from digest-verified copies in `runtime/provider_contracts/` and records `PROVIDER_INTERACTION_RESOLVED` or `PROVIDER_INTERACTION_REFUSED`. Anthropic and OpenAI both currently declare `NO_APPROVED_AUTOMATION_SURFACE`, because their terms withhold automated access to their consumer products, so resolution refuses with FAIL_CLOSED `PROVIDER_AUTOMATION_SURFACE_APPROVED`; it contacts no provider and starts no browser. Invoking StegBrowser from a resolved surface is a later step, taken only once a provider's contract is `APPROVED` with its explicit written automation permission.

## Provider capability contract

`runtime/contracts/provider-capability.schema.json` (`sv-llm.provider-capability/v0.1`) fixes the structure of each `SV-LLM/<Provider>` repository's `capability.json`. `runtime/provider_capability.py` is the offline validator those repositories vendor byte-for-byte (each records its sha256 in `validator_ref`). It returns ALLOW, DENY or FAIL_CLOSED: FAIL_CLOSED for malformed declarations or unbound provenance; DENY for authority claims, credential or endpoint material, live-invocation or runtime-observation claims, an authentic interface without a receipt, a consumer product declared as an automation surface, or a foreign identity. Negative fixtures are in `tests/fixtures/provider_capability/negative/`. The validator contacts no provider, and its disposition is evidence about a source file, not a transition.
